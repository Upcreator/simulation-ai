# LangGraph Simulation — MVP

Прототип долгоживущей ролевой симуляции для сценариев вида "ты — протагонист,
вокруг тебя разворачивается сюжет с NPC". LLM не хранит ничего между
запросами — весь контекст (кто ты, правила ведущего, мир, ростер
персонажей, хроника событий) лежит в markdown-файлах и пересобирается заново
на каждый ход. Оркестрация — на **LangGraph**, мониторинг — через
**Langfuse**, модель — через OpenAI-совместимый **прокси**.

> ⚠️ Это MVP-прототип, не production-билд.

## Как это работает

Ты играешь протагониста. На каждый ход пишешь, что делаешь/говоришь — или
корректируешь то, что уже произошло. Ведущий (LLM в роли GM):

1. Молча принимает твои корректировки как свершившийся факт.
2. Разворачивает сцену — вводит нужных NPC из ростера персонажей.
3. Ведёт диалог NPC в их характере (не подстраивается под тебя без причины).
4. Никогда не говорит и не действует за тебя самого.
5. Завершает ход разделом «Итоги» от лица ведущего — подмечает
   закономерности, связывает с хроникой прошлых событий.

```
Твой ход (действие / реплика / корректировка)
       │
       ▼
Загрузка markdown (skill, протагонист, мир, ростер NPC, хроника)
       │
       ▼
PromptBuilder собирает системный промпт
       │
       ▼
LLM генерирует ход: сцена + реплики NPC + итоги
       │
       ▼
Если накопилось много реплик — сжатие в хронику (memory/history.md)
       │
       ▼
Ответ показывается в чате
```

## Персонажи / NPC (personas/)

Каждый NPC — независимый markdown-файл. Ведущий сам решает, кого и когда
ввести в сцену, опираясь на карточки. Добавление нового NPC = создание
нового `.md`-файла (через UI во вкладке «🌍 Мир и персонажи» или руками).

## Протагонист (skills/protagonist.md)

Кто такой «ты» в симуляции: имя, должность, полномочия, характер, текущий
контекст задачи. Ведущий никогда не придумывает за тебя реплики или решения —
только реагирует на то, что ты реально написал в ходе.

## Правила ведущего (skills/skill.md)

Как модель должна себя вести в роли GM: порядок обработки хода, формат
ответа, ограничения (например, "не отвечай за протагониста"). Редактируется
через UI, меняется сразу — это system-level поведение всей симуляции.

## Мир (skills/world.md)

Сеттинг: эпоха, институты, атмосфера. Общий фон для всех NPC и сцен.

## Память (memory/history.md)

Единственная постоянная память всей симуляции. Когда в рабочем треде
накапливается больше `MAX_MESSAGES_BEFORE_SUMMARY` сообщений, старые реплики
сжимаются моделью в структурированную запись (заголовок / участники / суть /
последствия) и дописываются в конец `memory/history.md`. При каждом ходе вся
хроника целиком подгружается в промпт — так ведущий помнит прошлые события
даже после смены рабочего треда или перезапуска приложения.

MVP намеренно не решает проблему бесконечного роста файла — это explicit
non-goal на этом этапе. `load_history()` в будущем можно заменить на
`Retriever.search(...)`, не меняя граф, который её вызывает.

## PromptBuilder (src/prompt_builder.py)

Единственная ответственность — собрать финальный системный промпт:

```
skill.md + protagonist.md + world.md + ростер всех personas/*.md + memory/history.md
```

Никакой бизнес-логики внутри — только загрузка и конкатенация.

## LangGraph-граф (src/graph_simulation.py)

Один линейный граф: `narrate` (строит промпт через PromptBuilder, зовёт LLM)
→ `memory` (сжимает старые реплики в хронику, если пора) → конец хода.

`SqliteSaver` хранит короткий рабочий хвост сообщений текущего треда — не
источник истины для долгой памяти (им остаётся `memory/history.md`), а
буфер, чтобы модель видела недавний контекст дословно, без искажений
сжатия. При загрузке страницы интерфейс восстанавливает отображаемую
историю прямо из чекпоинтера — симуляция продолжается с того места, где
её оставили.

Кнопка «🔄 Новая симуляция» создаёт новый рабочий тред (короткий контекст
обнуляется), но не трогает `memory/history.md` — общая хроника остаётся
частью продолжающейся истории. Полная очистка памяти — отдельной кнопкой
во вкладке «🌍 Мир и персонажи».

## Установка

```bash
git clone <твой-репозиторий>
cd langgraph-simulation
python -m venv venv
source venv/bin/activate  # Windows: venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env
# заполни .env своими ключами
python app.py
```

Открой http://localhost:7860, во вкладке «🌍 Мир и персонажи» заполни
протагониста, правила, мир и добавь пару NPC — и можно начинать вести
симуляцию.

## Docker

```bash
docker build -t simulation .
docker run -p 7860:7860 --env-file .env \
  -v $(pwd)/personas:/app/personas \
  -v $(pwd)/skills:/app/skills \
  -v $(pwd)/memory:/app/memory \
  -v $(pwd)/data:/app/data \
  simulation
```

Все четыре volume-а важны: без них персонажи, правила, протагонист, мир и
хроника, изменённые через UI, будут теряться при пересоздании контейнера.

## Известные ограничения прототипа

- Хроника — простой markdown-файл без векторного поиска; при очень долгой
  симуляции будет расти без ограничения (осознанный компромисс MVP).
- Одна активная симуляция за раз (фиксированный набор протагонист/мир/NPC).
  Несколько параллельных независимых симуляций потребуют доработки —
  например, отдельных наборов файлов на "сценарий" вместо общих
  `skills/`/`memory/`.
- Ведущий получает ростер NPC целиком на каждый ход — при большом числе
  персонажей стоит следить за размером карточек, чтобы не раздувать промпт.
